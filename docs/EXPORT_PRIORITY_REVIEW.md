# Export priority — local review

Branch: `codex/export-priority`, based on local-main `344b1b2`. Review checkout: `velorn-mcp-parity`. No push, release, main merge, version bump or changes to the original dirty checkout are part of this follow-up.

## Evidence and scope

Two exports of Meme World Loop (102.29 seconds, 2,455 frames, 1080p24, libx264, GPU compositing, 19 WebCodecs sources) took 10m36s and 2m15s. Measured scheduling waits were 215.73 and 1.34 ms/frame, respectively. Decode/composite/pipe phases were slightly slower in the faster run. The maintainer reported editing/playback during the first run, and the main log recorded corresponding preview/autosave activity. That correlation does not establish the precise OS scheduling trigger.

The exporter yielded to `requestAnimationFrame` every four frames unless `document.visibilityState` was hidden. A real never-shown Electron window reports visible with background throttling disabled; that visibility check therefore cannot reliably protect an offscreen renderer from refresh-callback starvation.

## Implementation

- `exportScheduler.mjs` uses a per-export MessageChannel task queue in explicitly offscreen workers. Foreground browser exports retain periodic repaint yields. Cancellation, decoder delivery and IPC still receive task boundaries; scheduler ports are disposed on every exit. Diagnostics retain `uiYield` and add `progressYield`, `taskYield` and scheduling mode.
- `ExportJobRegistry` owns revisioned native activity. The preload exposes a read and removable subscription, with begin/progress/cancelling/terminal events. An older initialization read or late job event cannot unlock a newer export. Constructor/URL/load failures, worker crashes and premature close release activity.
- Renderer-only leases cover UI preparation/browser exports and UI/MCP queue gaps. The app switches to Export, releases the editor preview tree, pauses timeline/source and document media, blocks shortcuts and pointer actions, and defers periodic autosave until the render is done. HTML thumbnail autoplay cannot restart while busy. Playback does not resume automatically.
- The progress dialog retains cancellation and window controls; UI queues also retain Pause after current. Cancellation during destination selection prevents later worker startup. A failed cancellation remains locked and offers a retry. Cancel pauses remaining UI targets or cancels the current session's MCP batch targets.
- Native and renderer MCP policy guards reject new authored/heavy operations while rendering. Cheap inspection/status and cancellation remain accessible; unknown future actions fail closed. Existing preview/apply/context/Undo contracts remain intact.
- Raw-frame FFmpeg sessions are bound to their exact renderer. Crash/destruction aborts only that owner's encoders, settles blocked writes and removes session listeners. Normal encoder choices and output settings are unchanged.

## Follow-up: stalled GPU readback (2026-09-18)

After the scheduling fix, a real 2,455-frame export still took 16m59.8s. Scheduling was only 0.16 ms/frame; GPU readback was 378.33 ms/frame, approximately 929 seconds of that run. A synthetic GPU test was fast and did not reproduce this condition. Instrumentation in the actual app did: a three-second / 72-frame export took 32.318s, with 25.112s spent polling unsignaled GPU fences but only 0.108s collecting their completed buffers. The renderer was hardware ANGLE/OpenGL on the RTX 5090, not a software renderer. The exact Chromium/driver trigger remains unknown.

- GPU readback now has a 50 ms cooperative fence-poll budget. If exceeded, it collects that ticket's original PBO synchronously, drains older tickets in order, then uses synchronous GPU readback for the rest of this export. Rendering still uses GPU composition; encoder, resolution, effects and quality settings are unchanged. A new compositor starts with the normal asynchronous path again. The budget bounds polling, not a blocking driver call.
- Cancellation is checked during polling and after pipe backpressure. Missing/failed fences and context loss fail explicitly instead of passing possibly invalid pixels to the encoder. Constant-size readback diagnostics record the path and timing without per-frame logging.
- Cached, detached preview videos are paused before switching workspaces can unmount the preview. Pausing this cache alone did not fix the stall: the separate control still took 30.136s. No media is evicted and playback is not automatically resumed.
- Faster decoding exposed an existing one-microsecond source-frame boundary overlap. Independently rounding MP4 CTS, edit offset and duration could select the previous frame depending on whether the next decoded frame had arrived. Normalize in the container timebase first, then derive duration from the rounded start/end boundaries. This preserves GOP/decode ordering, genuine gaps and preroll while removing delivery-timing dependence.

The actual short export with adaptive recovery completed in 9.311s (versus 32.318s before); readback fell from 350.58 to 34.51 ms/frame. These short-run figures include startup and are not a forecast for every timeline. Diagnostic exports use `/tmp/velorn-export-trace-E99WLd`; the original project media and authored timeline were not edited. Unlike the earlier disposable-project fixtures, these follow-up comparisons deliberately use the maintainer's open project in the normal review app.

Full-length run `native-fixed-full-crf16.mp4` completed in **185.552s (3m05.6s)**, versus the logged **1019.768s (16m59.8s)** slow UI run, about **5.5× faster**. Both contain 2,455 frames / 102.291667s, 1920×1080/24fps, 19 WebCodecs sources, GPU composition and libx264 medium CRF16 (the x264 bitstream settings match). Readback fell from 378.33 to 27.62 ms/frame, with one fallback and no context loss. The test used MCP audio defaults (44.1kHz AAC versus the earlier UI's 48kHz AAC); this is a real-project video-path comparison, not a fully controlled all-settings benchmark. Existing saved UI export settings were not modified. Output has stereo audio and the expected frame count. Development auto-reload interrupted one earlier diagnostic run; its worker was stopped, and the successful run was performed only after edits/tests had settled. Avoid editing fixture/source files while benchmarking against a live Vite server.

Final validation: ffprobe confirmed those video dimensions/rate/frame count and the stereo AAC stream; a complete FFmpeg `-xerror` decode of both streams passed. Matching review frames at 35 seconds were visually inspected. The native job completed/unlocked, and Meme World Loop remained open on the same timeline. No commit, merge or push was performed.

This is export prioritization, not an OS resource scheduler: work already started in ComfyUI, external programs, or pre-existing asynchronous jobs is not silently killed. Cross-origin embedded applications cannot be paused by traversing Velorn's document. Native-only MCP entry points see native export activity; renderer preparation guards begin earlier. Pending MCP batches remain renderer-session-only, as documented before this work.

### Separate decoder limitation observed

That full-app fresh-profile test took 29.7s (repeat 33.2s), despite scheduling waits of only 0.14/0.12 ms/frame. Its export worker reported `VideoDecoder` unavailable, while the main renderer exposed it; `EncodedVideoChunk` existed, the worker was a secure loopback context, and the WebCodecs kill switch was unset. It therefore used the existing slower video-element path (`frameSources: null`), with roughly 104–107 ms/frame sampling and 84–105 ms/frame readback. Direct frame pipe and GPU compositing were active. The original user exports had 19 WebCodecs sources, so this is a different limitation, not evidence that removing refresh waits makes all exports universally fast. No decoder availability/configuration changes were made. Diagnostics are in the isolated test directory's `results.json` and `worker-diagnostic.json`; investigate separately if it occurs in a normal user session.

Browser scripts accept `PLAYWRIGHT_MODULE_PATH` and `VELORN_TEST_URL` (isolated Vite at 5198); add `VELORN_TEST_ELECTRON=1` for the Electron UI run. Native activity/scheduling fixtures do not start the normal app or its MCP server. Generated artifacts stay in temporary directories, outside the repository and user projects.

Windows/macOS packaged runtime testing remains required before release; the shared scheduling/UI code contains no Linux-specific production path. Manually review with a restarted Electron process, then compare an idle export with the old problem case. The editor should remain locked during render and be usable again after completion/cancellation/failure.
